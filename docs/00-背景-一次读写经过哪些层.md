# 00 · 背景：一次读写经过哪些层

> 不理解分层，就容易把"读不到"归因错：是权限、是属性不存在、还是下层没实现？
> 这一页把链路拆开。

---

## 1. 分层

```
┌──────────────────────────────────────────────┐
│ App                                          │
│   Car.createCar → connect → getCarManager    │
├──────────────────────────────────────────────┤
│ CarService（system_server 进程）              │
│   入口校验、权限检查、属性路由                 │
├──────────────────────────────────────────────┤
│ Vehicle HAL（vendor 进程）                    │
│   VehicleProperty 注册表、get/set、订阅       │
├──────────────────────────────────────────────┤
│ MCU / CAN / 各 ECU                            │
│   真正的物理执行                              │
└──────────────────────────────────────────────┘
```

每一层都可能让一次操作失败，而且失败表现不同：

| 层 | 失败表现 |
|---|---|
| App | 连接失败、`getCarManager` 返回 null |
| CarService | `SecurityException`、入口校验拒绝 |
| VHAL | 属性不存在、返回 null、status 非 0 |
| MCU/ECU | 返回成功但值不变（静默丢弃） |

所以排查顺序应该是：**连接 → 入口 → 属性存在 → 写入是否被下层接受**。

---

## 2. Car 与 Manager

`android.car.Car` 是入口，通过它拿到不同的 manager：

| manager 名 | 典型用途 |
|---|---|
| `"property"` | 通用属性读写（最常用） |
| `"cabin"` | 座舱相关（部分厂商扩展方法） |
| `"mcu"` | 厂商 MCU 隧道、int[] / byte[] 属性 |
| `"audio"` | 音量、静音 |
| `"sensor"` | 传感器事件（`getLatestSensorEvent`） |

不同车型/版本可用的 manager 名可能不同。拿不到就返回 `null`，不要假设它一定存在。

连接骨架（反射写法，避免编译期依赖）：

```java
Class<?> carClass = Class.forName("android.car.Car");
Method createCar  = carClass.getMethod("createCar", Context.class, ServiceConnection.class);
Method carConnect = carClass.getMethod("connect");
Method getManager = carClass.getMethod("getCarManager", String.class);

car = createCar.invoke(null, context, conn);  // 静态方法
carConnect.invoke(car);
```

要点：

- `createCar` 是静态方法；
- 连接是异步的，要等 `onServiceConnected`；
- 熄火/休眠后 Binder 可能"假连接"，读写抛异常时要重建。

完整实现见 [examples/VhalClient.java](../examples/VhalClient.java)。

## 3. 属性 ID 是怎么编出来的

VHAL 属性 ID 是一个 32 位整数，通常按位域编码：

```
bit 31..28   Group    谁定义的（AOSP / 厂商 / 供应商）
bit 27..24   Area     按什么维度分区（全局 / 座位 / 车门 / 车窗）
bit 23..16   Type     值的类型（int / float / bool / string / bytes）
bit 15..0    Property 具体属性编号
```

不同厂商的具体划分可能不同，但**知道有这四段**，就能大致判断一个 ID 属于哪一类，
也能理解为什么同一个属性会有多个 area。

举例（仅示意，不是本仓库的权威表）：

```
0x11400400
  Group = 0x1
  Area  = 0x1
  Type  = 0x40
  Prop  = 0x0400
```

要看自己车上的真实编码，最快的方法是：

1. 枚举出全部属性；
2. 按 Group/Area/Type 分组；
3. 结合属性名和实测值反推。

属性名通常在 VHAL 的 `VehicleProperty` 常量表里，反编译 framework 或 vendor 的
`VehicleProperty.java` 可以看到。

## 4. 一次读的时序

```
App: getIntProperty(id, area)
  → CarService: 校验调用方、路由
    → VHAL: 查注册表
      → 有缓存值：返回缓存 + 状态
      → 无缓存：向 MCU 请求（可能超时）
  ← 返回 CarPropertyValue(value, status, timestamp)
```

理解这一点可以解释两个常见现象：

- **第一次读很慢**：VHAL 可能要去 MCU 取；
- **读到的值不更新**：可能是缓存，需要订阅或重新读。

---

## 5. 一次写的时序

```
App: setIntProperty(id, area, value)
  → CarService: 校验、路由
    → VHAL: 检查属性可写性、值域
      → MCU/ECU: 执行
        → 失败时可能：
           a) 抛异常
           b) 返回 false
           c) 返回 true 但值不变（静默丢弃）
```

第三种最坑，所以写入之后**必须回读**，见 [03-写入](03-写入-怎么确认写成功.md)。

---

## 6. 小结

- 分层决定了失败原因：权限、属性存在性、下层实现，是三件不同的事；
- 属性 ID 是位域编码，理解它有助于自己分析；
- 读可能走缓存，写可能静默失败；
- 所有具体 ID、area、值域，都应该从你自己的车上枚举出来。
