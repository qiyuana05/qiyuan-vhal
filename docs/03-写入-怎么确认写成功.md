# 03 · 写入：怎么确认写成功

> 写入最危险的不是报错，而是"返回成功但值没变"。
> 这一页的核心只有一句：**写完必须回读**。

---

## 1. 写入口

和读取对应：

| 方法 | 参数 |
|---|---|
| `setIntProperty(id, area, value)` | int 属性 |
| `setFloatProperty(id, area, value)` | float 属性 |
| `setBooleanProperty(id, area, value)` | boolean 属性 |
| `setStringProperty(id, area, value)` | string 属性 |
| `setBytesProperty(id, area, bytes)` | byte[] 属性 |
| `setIntArrayProperty` / `setVecProperty` | 数组属性 |

有些厂商 manager（例如 `mcu`）使用 `setIntVecProperty(id, int[])` 之类的方法，
参数形态不同，需要按实际反编译结果调用。

---

## 2. 写之前必须确认的三件事

### 2.1 属性是否声明可写

枚举结果里的 `access`：

- `1` = READ：理论上不可写；
- `2` = WRITE：可写；
- `3` = RW：可读可写。

但 `access` 只是声明。声明可写不代表下层实现，声明只读也不代表一定拒绝。

### 2.2 area 是否正确

多区属性（温度、车门、车窗、座椅）必须传对 area。
传错的表现通常是：

- 返回成功但值不变；
- 值写到了别的区；
- 抛 `IllegalArgumentException`。

做法：遍历 `getAreaIds()`，逐个试读，确认哪个区对应你操作的位置。

### 2.3 值域是否合理

看 `getMinValue` / `getMaxValue`：

- `min == max == 0`：很可能是结构性拒写，别浪费时间去试；
- 有明确范围：按范围构造值；
- 枚举型：先读当前值，再根据语义尝试相邻值。

---

## 3. 回读验证流程

```
1. 写之前先读一次，记录 before 值
2. 写入
3. 等待一个合理间隔（几十毫秒到几百毫秒，视属性而定）
4. 再读一次，记录 after 值
5. 对比：
   - after == 目标值 → 成功
   - after == before  → 写入被忽略
   - after 是其他值   → 被下层修正/钳制
   - 读异常/status≠0  → 属性或连接异常
```

### 3.1 为什么要等

部分属性不是同步生效：

- MCU 需要处理时间；
- 某些值会被平滑/钳制（例如温度不允许跳变过大）；
- 状态回读可能滞后。

如果一次回读没变，可以隔 100~500ms 再读一次，但不要无限重试。

---

## 4. 写入的四种结果

| 结果 | 含义 | 下一步 |
|---|---|---|
| 返回成功 + 回读一致 | 真正生效 | 记录值域和 area |
| 返回成功 + 回读不变 | 被静默丢弃 | 检查 access、min/max、area、下层实现 |
| 抛异常 | 权限/参数/类型错误 | 看异常类型和消息 |
| 返回 false | 明确拒绝 | 检查属性支持情况 |

**"返回成功 + 回读不变"是最常见的坑**，尤其在厂商自定义属性上。

---

## 5. 写入模板

```java
public boolean writeAndVerify(int id, int area, int target) {
    Object before = read(id, area);

    try {
        setInt.invoke(property, id, area, target);
    } catch (Throwable t) {
        return false;                      // 参数/权限/类型错误
    }

    sleep(150);

    Object after = read(id, area);
    return after instanceof Integer && ((Integer) after) == target;
}
```

完整实现见 [examples/VhalClient.java](../examples/VhalClient.java) 的
`writeIntAndVerify()`。

## 6. 风险分级

| 类型 | 例子 | 风险 | 建议 |
|---|---|---|---|
| 舒适性 | 空调温度、风量、座椅加热 | 🟢 低 | 可试，记录恢复方法 |
| 座舱 | 灯光、白天黑夜、音量、背光 | 🟡 中 | 可试，避免在驾驶中操作 |
| 车身 | 车窗、门锁、行李箱 | 🟠 中高 | 确认周围安全再试 |
| 驱动/动力 | 驱动模式、油门、扭矩 | 🔴 高 | 不要直接写 |
| 安全 | 制动、转向、气囊、电源 | 🔴 极高 | **禁止写** |

原则：

> 能读不等于该写；声明可写不等于安全。
> 不确定语义的属性，只读不写。

---

## 7. 写入失败排查顺序

1. **连接是否正常**：读一个已知稳定的属性试试；
2. **area 是否正确**：遍历 area 读一遍；
3. **值域是否越界**：看 min/max；
4. **属性是否真的实现**：换个同组属性对比；
5. **下层是否接受**：回读不变就是下层丢弃；
6. **是否需要先满足前置条件**：例如挡位、电源状态、其他属性。

---

## 8. 不要做的事

- ❌ 不要在不知道语义的情况下批量写；
- ❌ 不要写动力、制动、转向、电源相关属性；
- ❌ 不要在驾驶过程中写车身/座舱属性；
- ❌ 不要因为"返回成功"就认为生效；
- ❌ 不要把"能写"当成"应该写"。

---

## 9. 恢复方案

写入前先想好怎么恢复：

- 记录原始值，必要时写回；
- 对可逆的舒适性属性，准备"关闭/默认值"按钮；
- 对可能影响驾驶的属性，准备重启车机/恢复出厂方案；
- 不要在无法恢复的场景下做写入实验。
