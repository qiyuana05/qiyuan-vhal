# 01 · 发现：枚举你这台车的属性

> 别人的属性表只能当参考。真正要动手，第一步永远是在自己车上跑一遍枚举。

---

## 1. 为什么要枚举

VHAL 暴露的属性集合由三样东西决定：

- 平台（AOSP 版本、SoC）；
- 厂商在 `VehicleProperty` 里注册了什么；
- 具体车型/配置有没有接入对应 ECU。

所以同一款车不同年款、不同 OTA，属性数量、ID、area 都可能变。
枚举的意义是拿到**你这台车当前的真实清单**，而不是猜。

---

## 2. 枚举 API

核心是 `CarPropertyManager.getPropertyList()`：

```java
List<CarPropertyConfig> list =
        (List<CarPropertyConfig>) getPropertyList.invoke(property);

for (CarPropertyConfig c : list) {
    int    id     = (Integer) c.getClass().getMethod("getPropertyId").invoke(c);
    int    access = (Integer) c.getClass().getMethod("getAccess").invoke(c);      // 1=READ 2=WRITE 3=RW
    int[]  areas  = (int[])   c.getClass().getMethod("getAreaIds").invoke(c);
    int    mode   = (Integer) c.getClass().getMethod("getChangeMode").invoke(c);  // 0=静态 1=onChange 2=连续
    Object min    = c.getClass().getMethod("getMinValue", int.class).invoke(c, areas.length > 0 ? areas[0] : 0);
    Object max    = c.getClass().getMethod("getMaxValue", int.class).invoke(c, areas.length > 0 ? areas[0] : 0);
    // 部分版本还有 getMinSampleRate / getMaxSampleRate
}
```

### 2.1 每个字段怎么看

| 字段 | 含义 | 用法 |
|---|---|---|
| `propertyId` | 32 位属性 ID | 后续读写的 key |
| `access` | 1 READ / 2 WRITE / 3 RW | 判断"理论上能不能写" |
| `areaIds` | 该属性支持的 area 列表 | 读/写时必须传对应 area |
| `changeMode` | 变化模式 | 决定用轮询还是订阅 |
| `minValue` / `maxValue` | 值域 | **`min == max == 0` 往往意味着结构性拒写** |
| `minSampleRate` / `maxSampleRate` | 采样率 | 连续型属性才有意义 |

> `access` 只代表"声明"，不代表"写入一定生效"。很多属性声明 RW，但下层没实现。

---

## 3. 输出成 CSV

枚举结果建议直接落盘，方便后续筛选：

```csv
property_id_hex,property_id_dec,access,areas,change_mode,min,max
0x11400400,289408000,1,0,0,0,0
0x11600207,291504647,1,0,1,0,0
```

示例实现见 [examples/EnumProperties.java](../examples/EnumProperties.java)。

拿到 CSV 后，可以按这些维度筛：

- `access` 为 2 或 3 的，是"候选可写"；
- `areas` 多于 1 个的，通常是座位/车门/车窗/温区；
- `min == max == 0` 的，先当不可写；
- 同一 Group 下的 ID 往往属于同一子系统（空调、车身、动力等）。

---

## 4. 用 dumpsys 辅助

枚举拿不到属性名时，`dumpsys` 能补充上下文：

```bash
adb shell dumpsys car_service
adb shell dumpsys android.hardware.automotive.vehicle@2.0::IVehicle/default
```

重点看：

- 属性列表与值；
- 调用方权限；
- 是否有 `not supported` / `not implemented` 之类提示。

不同版本的 dumpsys 输出格式不同，抓关键字即可，不要依赖固定行号。

---

## 5. 不知道 ID 时怎么找

如果你已经知道"某个功能存在"，但不知道对应哪个属性，可以用盲扫：

1. 从枚举结果里筛出同 Group 的 ID；
2. 对每个 ID 尝试读（注意超时和异常）；
3. 操作车辆上对应的功能，再读一次，对比哪些值变了；
4. 记录"变化 + 方向 + 单位"，反推语义。

盲扫原则：

- **只读**，不写；
- 一次只操作一个功能；
- 记录操作前后的值和时间戳；
- 对返回 `-1`、`null`、`status != 0` 的 ID 先跳过。

---

## 6. 记录模板

建议给自己车的属性建一份本地记录（不一定要公开）：

```markdown
## 属性记录
- 车型 / 年款 / OTA：
- 枚举日期：
- 属性总数：
- 可写数量：

| ID | access | area | 类型 | 实测值 | 语义（已验证/推测） | 备注 |
|---|---|---|---|---|---|---|
```

**这份记录只对你这台车有效。** 换车、换版本要重来。

---

## 7. 不要做的事

- ❌ 不要把别人车上的属性 ID 表直接当自己的；
- ❌ 不要因为 `access=3` 就直接写——先读、先确认值域；
- ❌ 不要对枚举结果里的所有 ID 批量写入；
- ❌ 不要把含 VIN、设备标识的 dumpsys 原文公开。
